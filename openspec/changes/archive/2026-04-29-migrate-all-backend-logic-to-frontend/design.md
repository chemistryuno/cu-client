## Context

当前前端通过 `frontend/src/utils/api.ts` 统一调用远程 HTTP API，并在离线模式下仅对少量接口使用 `offlineBackend` 适配。项目的核心业务状态、鉴权、持久化、房间管理、实时通信与后台能力仍主要位于 `backend/`。本次变更不是简单地增加离线分支，而是把原本依赖服务端常驻进程的数据与业务职责迁移到前端运行时，使浏览器、Electron 与 Capacitor 宿主都能在无 Go 后端前提下完成主要业务。

这个目标是一个跨模块架构变更，涉及 API 访问层、前端状态模型、本地持久化、多人同步边界、权限信任模型以及构建发布流程。由于前端运行环境无法提供与服务端等价的信任边界，设计需要明确哪些能力可在纯前端单机化场景中成立，哪些能力只能在受信宿主或未来同步层存在时提供有限保证。

## Goals / Non-Goals

**Goals:**
- 用前端本地运行时服务替代当前依赖远程后端的 API 访问层。
- 用统一的客户端数据层承接用户、卡组、反馈、公告、反应物、生成物、配置和历史记录的持久化。
- 将游戏域规则、房间生命周期、回合推进、结算与回放逻辑迁移到前端。
- 保持现有页面和调用侧尽量通过兼容的 service 接口完成迁移，降低 UI 重写成本。
- 明确管理员与协作者能力在纯前端架构下的授权边界与适用范围。

**Non-Goals:**
- 不追求在纯浏览器场景下提供等价于中心化服务端的强安全保证。
- 不在本次设计中定义跨设备强一致同步协议或完整 P2P 联网协议。
- 不要求一次性删除全部后端代码；允许迁移期间保留对照实现与过渡适配层。
- 不改变现有页面的信息架构与视觉设计，重点是能力承载方式变更。

## Decisions

### 1. 以 `client runtime service` 替代 `axios API facade`
选择在前端引入统一的运行时服务层，而不是继续扩张 `offlineAxiosAdapter`。

- 方案 A：继续保留 axios 调用形态，在 adapter 内模拟所有路由。
- 方案 B：新增面向领域的本地运行时服务，并让 `api.ts` 逐步退化为兼容包装层。
- 决策：采用方案 B。
- 原因：当前接口已经覆盖认证、房间、反馈、管理员、化学数据等大量领域。继续把全部后端职责编码成“假 HTTP 路由”会让前端长期停留在服务端心智模型中，调试与类型建模也会越来越脆弱。独立运行时服务更适合承接领域状态、事务边界和宿主能力差异。

### 2. 以本地持久化仓储替代服务端 Repository
选择在前端定义与领域对应的 repository/store 层，底层按运行环境映射到 IndexedDB、本地文件或宿主存储。

- 方案 A：所有数据只保存在内存，刷新后丢失。
- 方案 B：引入统一存储抽象，浏览器默认 IndexedDB，Electron/Capacitor 可扩展到文件或插件存储。
- 决策：采用方案 B。
- 原因：后端职责中大量能力依赖持久化，包括账号资料、会话、卡组、历史记录、反应物和公告。只有统一存储抽象，才能在多个宿主保持一致的领域服务接口。

### 3. 游戏逻辑前移为纯前端领域引擎
选择将房间、裁判、化学反应校验、回合推进与结算下沉为纯前端可调用模块。

- 方案 A：把原接口数据结构保留下来，仅在 UI 层拼装状态。
- 方案 B：建立独立的游戏引擎模块，UI 只消费投影状态和命令结果。
- 决策：采用方案 B。
- 原因：房间状态、手牌、回合和反应规则本身具有强一致的领域约束，直接散落在页面状态中会导致逻辑重复和错误难以复现。独立引擎更容易测试与回放。

### 4. 多人实时能力按“本地优先、同步可插拔”设计
选择把当前 WebSocket Hub 职责抽象为前端会话总线，单机或同宿主场景由本地事件驱动，多端同步后续通过桥接层扩展。

- 方案 A：要求本次直接实现浏览器 P2P 或自建同步协议。
- 方案 B：先定义统一同步接口，默认使用本地事件总线，保留未来宿主桥接扩展点。
- 决策：采用方案 B。
- 原因：用户要求是“把所有后端逻辑移植到前端”，不是“立刻完成完整联网协议替代”。先收敛领域逻辑与状态模型，再为多端同步保留接口，落地风险更可控。

### 5. 权限模型改为“能力门控 + 受信宿主声明”
选择不再宣称纯前端具备后端式权限隔离，而是把管理员、协作者等能力定义为前端能力门控，并在设计上要求区分单机可信与开放环境。

- 方案 A：完全复制当前 JWT + middleware 权限语义。
- 方案 B：改为客户端角色能力门控，并对敏感操作标注信任前提。
- 决策：采用方案 B。
- 原因：前端代码和本地数据天然可被用户控制，无法提供服务端级别的防篡改。把边界写清楚比伪造等价安全模型更可靠。

## Risks / Trade-offs

- [纯前端权限不可防篡改] → 将管理员与协作者能力限定为单机或受信宿主场景，并在需求中明确不提供服务端级安全承诺。
- [本地持久化在不同宿主表现不一致] → 定义统一存储接口，并为浏览器、Electron、Capacitor 分别提供适配层与迁移脚本。
- [多人同步缺失会削弱原 WebSocket 能力] → 先保证单机和同端体验，保持同步接口可插拔，后续按宿主能力接入桥接实现。
- [迁移范围过大导致 UI 大面积联动] → 先保持 `frontend/src/utils/api.ts` 对调用方的兼容 facade，再逐步替换为直接 service 调用。
- [历史数据从后端数据库迁移到前端存储时可能丢失字段] → 定义导入导出格式，并把数据迁移纳入独立任务和验收场景。

## Migration Plan

1. 梳理现有 `api.ts` 暴露的领域边界，按认证、数据、游戏、管理拆分客户端运行时服务。
2. 建立统一本地存储抽象与数据模型，优先覆盖用户、卡组、反应物、生成物、配置和历史记录。
3. 把游戏引擎、房间状态机、结算与回放逻辑迁入前端纯函数/服务模块。
4. 让 `api.ts` 改为调用本地运行时服务，保留现有页面接口签名，逐步移除远程请求依赖。
5. 为管理员、协作者与同步接口补齐能力门控和宿主适配层。
6. 验证 Electron、Capacitor 和浏览器离线模式下的启动、持久化和核心流程。
7. 完成后再评估是否移除 `backend/` 对前端运行的剩余构建依赖。

回滚策略：在迁移过程中保留现有后端接口适配开关，使前端可以暂时回退到远程 API 模式；只有在本地运行时覆盖核心流程后，才删除旧链路。

## Open Questions

- 纯浏览器环境下管理员与协作者能力是否需要默认隐藏，只在 Electron/Capacitor 受信模式开放。
- 当前 WebSocket 驱动的多人对局是否需要在本次迁移中降级为同机/热座模式。
- 是否需要提供从现有后端数据库导出并导入前端本地存储的迁移工具。
- WebAuthn、2FA、邮件验证码这类依赖外部信任源的能力，在纯前端模式下是保留占位、改为宿主桥接，还是降级为本地安全设置。
