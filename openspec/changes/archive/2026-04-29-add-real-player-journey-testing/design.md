## Context

当前前端已经可以在本地离线模式下运行，且教程、大厅、建房、房间、回放、资料页等玩家路径都已有实际页面与运行时逻辑，但验证方式主要还是手工体验与编译检查。用户要求的是“模拟真实玩家点击操作”的测试，不是只调用 API，也不是只做单元测试，因此设计重点是建立一套以浏览器页面操作为中心、能稳定重放完整玩家旅程的测试能力。

这项工作是跨页面、跨运行时状态、跨前端配置的变更。它会触及页面选择器稳定性、测试前状态清理、离线运行时数据播种、等待条件和测试脚本组织方式。由于当前项目里还没有现成的 e2e 测试目录或框架，设计需要同时解决测试运行器、环境准备和断言边界问题。

## Goals / Non-Goals

**Goals:**
- 建立可以模拟真实玩家点击操作的浏览器级端到端测试能力。
- 覆盖从首次进入教程到进入真实对局并完成关键操作的主玩家旅程。
- 为登录/离线身份初始化、大厅、建房、加入房间、对局操作、资料页、历史/回放和若干相关功能建立稳定的回归测试。
- 提供测试前状态复位与数据初始化能力，让测试可重复执行。
- 让这套测试能接入本地开发验证流程。

**Non-Goals:**
- 不把所有业务逻辑都改写成单元测试。
- 不在本次设计中引入云端测试基础设施或跨浏览器矩阵。
- 不依赖真实后端联网环境；优先使用当前前端离线运行时完成玩家链路验证。
- 不要求一次性覆盖每个页面细节，重点先覆盖高价值玩家路径。

## Decisions

### 1. 采用浏览器自动化 e2e，而不是 API 驱动测试
- 方案 A：直接调用 `api.ts` 或 runtime service 做“伪端到端”测试。
- 方案 B：使用浏览器自动化框架，从页面点击、输入、跳转和可见断言角度执行测试。
- 决策：采用方案 B。
- 原因：用户明确要求模拟真实玩家点击操作，只有浏览器自动化才能覆盖教程弹层、按钮状态、页面跳转、路由和 UI 连续交互。

### 2. 以离线运行时作为默认测试环境
- 方案 A：等待完整后端环境后再做测试。
- 方案 B：基于当前 `OFFLINE_MODE` 和本地 runtime 建立测试。
- 决策：采用方案 B。
- 原因：当前前端已经能在本地离线模式运行，而且测试目标是持续验证玩家链路；离线环境更可重复，也更适合在迁移期快速回归。

### 3. 增加“测试稳定化层”，而不是在脚本里散落临时等待
- 方案 A：在测试脚本中大量使用固定 sleep。
- 方案 B：为测试添加可复位状态、稳定选择器、显式等待条件和测试数据播种入口。
- 决策：采用方案 B。
- 原因：教程、房间状态和离线数据都依赖本地状态，如果没有稳定化层，测试会脆弱且难维护。

### 4. 先覆盖高价值玩家主线，再补功能回归套件
- 方案 A：一次性把所有功能写成大而全的测试。
- 方案 B：先建立主玩家旅程，再增加资料页、回放、反应式、物质等回归场景。
- 决策：采用方案 B。
- 原因：从教程到真实游戏的主链路最能体现是否“能玩”，其他相关功能则作为第二层回归保障。

## Risks / Trade-offs

- [页面结构变动导致选择器失效] → 为关键路径增加稳定的测试选择器，避免依赖纯样式类名。
- [离线状态残留导致测试不稳定] → 在每次测试前清理本地存储并提供统一播种入口。
- [教程/房间流程包含异步状态切换] → 使用显式可见断言、URL 断言和运行时状态等待，而不是固定延时。
- [测试覆盖越多，维护成本越高] → 先锁定高价值主流程，再分层补充其他回归场景。
- [当前项目尚无现成 e2e 基础设施] → 先引入最小可用测试框架与本地命令，再逐步扩展。

## Migration Plan

1. 选定并接入浏览器自动化测试框架与脚本命令。
2. 为登录、教程、大厅、房间、资料页、回放等关键页面补稳定测试钩子。
3. 增加测试前状态清理和数据播种能力。
4. 实现“教程 → 建房/开始 → 房间操作 → 历史/回放”的主玩家旅程测试。
5. 实现资料页、反应式、物质等相关功能回归测试。
6. 将测试接入本地验证流程，并记录运行方式。

回滚策略：新增测试能力应尽量通过独立脚本、配置和测试专用钩子引入；若影响生产运行，可先禁用测试入口但保留业务代码不变。

## Open Questions

- 测试框架选 Playwright 还是其他浏览器自动化方案。
- 是否需要为某些复杂流程增加测试专用 query 参数或全局钩子。
- “真实游戏”在离线环境下是指 AI 对局、双本地玩家，还是两者都要覆盖。
- 其他相关功能的首批范围是否固定为资料页、历史/回放、反应式和物质页。
