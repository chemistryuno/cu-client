## Context

当前游戏房间同时承载战场信息、手牌操作、输入反馈、教程提示和房间状态变化，但通知能力仍然是分散插入到各个局部区域的临时展示。结果是同类消息在不同区域使用不同样式与动画，有些提示停留太久、遮挡主视区，有些提示又过于轻微而被忽略。

本次变更既是信息架构调整，也是视觉风格升级。它需要同时覆盖登录后的主界面设计语言、房间内通知层级、页面动效节奏以及共享 UI 组件的复用方式。由于用户明确要求“告知玩家但不干扰页面显示”，设计重点不在于增加更多弹层，而在于建立一套低干扰、高可识别、可复用的房间通知系统。

该改动会跨越 `GameRoom.vue`、登录/大厅/房间的共享样式、现有 toast 或提示条逻辑，以及潜在的轻量第三方动画/通知库接入方式。因此需要在编码前统一通知优先级、布局锚点和动效策略，避免后续继续堆叠局部修补代码。

## Goals / Non-Goals

**Goals:**
- 建立统一的房间内通知分层，明确哪些事件使用常驻状态提示、哪些使用短时反馈、哪些使用弱提示辅助。
- 让重要消息在 1 次视线扫视内可发现，同时避免遮挡中央战场、手牌区和主要操作按钮。
- 将通知样式纳入新的控制台式视觉语言，和登录界面、主界面、游戏房间保持一致的设计语气。
- 通过轻量第三方库复用进入/离场动画或消息容器能力，减少自写样板代码。
- 控制页面总高度和元素密度，删除不必要的装饰性提示块，提升房间信息压缩度。

**Non-Goals:**
- 不在本次设计中重做游戏规则、房间流程或消息触发来源。
- 不引入需要复杂后端配合的实时推送系统。
- 不把所有历史提示都做成可回看的消息中心；本次只聚焦房间内即时展示。
- 不追求高强度炫技动画，避免新的视觉疲劳问题。

## Decisions

### 1. 建立三层通知模型，而不是继续沿用单一 toast
- 方案 A：保留现有 toast/浮层思路，只微调位置和样式。
- 方案 B：把房间提示拆分为“顶部状态条”“角落事件流”“上下文辅助提示”三层。
- 决策：采用方案 B。
- 原因：房间内事件的优先级差异很大。回合归属、房间阶段变化这类信息适合稳定锚定展示；抽牌、出牌结果等适合角落短时反馈；教程/引导类则应以贴近上下文的弱提示呈现。单一 toast 无法同时兼顾可见性和低干扰。

### 2. 固定通知安全区，禁止侵入核心操作区域
- 方案 A：继续在页面中心或组件附近直接浮出消息。
- 方案 B：为房间建立固定安全区，优先使用顶部横向状态区和右上角纵向事件区，中心战场仅保留极少数必要状态强调。
- 决策：采用方案 B。
- 原因：用户的主要注意力集中在战场中央、手牌底部和确认操作区。通知应避开这些区域，只在必须时短暂借用中心区域，否则会与核心交互竞争注意力。

### 3. 使用轻量动效库统一入场/退场，而不是为每种提示手写动画
- 方案 A：继续用零散 CSS transition/animation。
- 方案 B：引入轻量动画或通知容器库，例如 `@formkit/auto-animate` 用于列表重排/出入场，配合现有 Vue transition 或极轻量 toast 容器库管理消息堆栈。
- 决策：采用方案 B，以“轻量、可局部接入、不改变现有状态管理”为前提。
- 原因：本次目标之一是节省代码空间并降低样板代码。轻量第三方库更适合处理消息队列的平滑衔接、重排与离场，避免继续复制大量过渡类名和手写计时逻辑。
- 备选说明：若现有项目已包含足够的过渡能力，则优先复用现有依赖，只在消息栈动画和容器编排上补最少新库。

### 4. 动效采用“短距离、低振幅、先快后稳”的控制台节奏
- 方案 A：使用明显滑入、放大、闪烁等强提示动画强化存在感。
- 方案 B：用 160ms 到 280ms 的短距离位移、透明度过渡和轻微描边闪动，重要通知使用一次性强调，不循环闪烁。
- 决策：采用方案 B。
- 原因：用户明确不希望视觉疲劳。房间通知必须被看见，但不能持续争抢焦点。控制台风格更适合克制、精准、带方向感的微动画，而不是反复跳动的强刺激动效。

### 5. 收敛页面纵向占用，删除重复说明元素
- 方案 A：在现有布局上叠加新的通知容器。
- 方案 B：借通知系统重构，顺带删减重复标题、冗余边框块、低价值装饰标签，将状态提示并入统一栏位。
- 决策：采用方案 B。
- 原因：用户已明确要求页面“纵向太大了，压缩一点，删除一些不必要的元素”。如果只新增通知层而不整理布局，最终仍会使房间更拥挤。

## Risks / Trade-offs

- [通知优先级划分不当，导致关键信息被弱化] → 先定义事件分类表，至少覆盖回合变更、出牌结果、惩罚/结算、房间状态、教程提示五类，并在实现阶段逐项映射。
- [接入第三方库带来样式冲突或额外体积] → 只选择无重 UI、可树摇、专注过渡编排的轻量库，并限制其使用范围在共享通知容器层。
- [多个通知同时出现时仍造成堆叠混乱] → 限制并发数量，按优先级覆盖或排队；低优先级消息超量时折叠为计数提示。
- [房间与登录/大厅风格统一后，现有局部组件显得突兀] → 先抽离通用颜色、边框、阴影和动效 token，让页面逐步切换到统一风格。
- [过度压缩布局导致新手理解成本上升] → 保留必要标签和新手提示，但将其改为可收起、弱化或上下文触发，而不是常驻大块说明区。

## Migration Plan

1. 盘点当前房间内所有通知来源，按优先级和展示目标归类。
2. 定义统一的通知容器、视觉 token 与布局安全区，并确定第三方库接入点。
3. 替换房间中的临时 toast/提示块，先接入顶部状态区和角落事件流。
4. 收敛教程提示、房间状态提示和 PvE/回放反馈的展示方式，去掉重复元素。
5. 同步更新登录界面和主界面共享风格变量，保证通知和整体视觉语言一致。
6. 在主要房间流程中验证通知不会遮挡关键操作，并根据体验微调停留时长和动效强度。

回滚策略：通知系统应通过独立容器和样式变量引入；若新方案存在严重可用性问题，可切回旧的消息触发逻辑并保留新的样式 token，不影响游戏核心流程。

## Open Questions

- 当前项目是否已经引入可复用的 toast/transition 基础设施，可替代新增库的一部分能力。
- 房间内是否需要保留一份最近通知的极简历史记录，以便玩家错过短时消息后快速回看。
- 回放模式与实时对局是否共用同一套通知节奏，还是需要更弱的提示强度。
- 教程提示是否需要在新风格下支持“首次强提示、重复弱提示”的降噪策略。
